Gateway & Response

In: request context (current video, device, locale) and the user's A/B bucket.
Out: the final slate plus an impression log keyed by request ID, which feeds nearline and offline.

Key pointEach stage filters for the next. A great Ranking model can't rescue a video that Retrieval never surfaced, so monitor every stage, not only the final slate.

Pro
Lowest latency, mature
Con
No cross features
Fit
Tight budget, huge candidate sets

Three-tower late + light cross

Pro
Caching + cross features
Con
Cross tower runs per item
Fit
Feeds with real-time stats

COLD-style early fusion

Pro
Early fusion, most accurate
Con
Little caching, compute-aware tuning
Fit
Ads, e-commerce
Whichever you pickDistill from Ranking, and measure how much of Ranking's top-k survives.

Evaluation

Multi-layer experiments · teams test in parallel

Launch layersshipped baselineevery request passes first, then a domain
Columns = domains, exclusiveRows = layersexp Base = control no bucket
01Domain · exclusive splitHash user ID into one domain · strategy domains run a fixed path, compared with Baseline
02Layer · reuse trafficOwn hash seed per layer · exclusive within, free combination across
03Conditions at the layerMatch first, then hash · exp and control share one population
04Ramp up, no switchingFixed bucket ranges · exp grows up from 0, control down from the top
Param override · low → highdefault→Launch layer→Domain experimentChange only the delta · the rest inherits the baseline
RememberOrthogonal buckets ≠ independent effects: a new retrieval source changes what Ranking sees.
